# KeyStats synchronization protocol v1

This directory is the wire-level source of truth shared by the macOS client,
Windows client, and Cloudflare Worker. The service receives only the encrypted
record shape; `CoreDaySnapshotV1` is serialized, validated, encrypted, and
decrypted exclusively by clients.

## Cryptographic conventions

- The vault seed is exactly 16 bytes. A recovery code is 26 Crockford Base32
  payload characters followed by two checksum characters. Decoders accept
  hyphens/whitespace and the Crockford `O -> 0`, `I/L -> 1` aliases, then verify
  the canonical checksum.
- HKDF-SHA256 uses an empty salt and the exact UTF-8 `info` labels in
  `fixtures/crypto-vectors.json`.
- Record IDs are unpadded base64url HMAC-SHA256 over
  `deviceId + "\\n" + localDay`, keyed by `record-index-v1`.
- AES-256-GCM records use a fresh random 12-byte nonce and a 16-byte tag. AAD is
  the exact UTF-8 string
  `1\\nvaultId\\ndeviceId\\nrecordId\\nrevision`.
- `ciphertextHash` is unpadded base64url SHA-256 over the decoded bytes
  `nonce || ciphertext || tag`. It is an idempotency aid, not a replacement for
  GCM authentication.
- Pairing uses X25519, HKDF-SHA256 `pairing-wrap-v1`, and AAD
  `1\\nsessionId`. The six-digit safety code is the big-endian first 32 bits of
  SHA-256 over `pairing-safety-code-v1 || min(pubA,pubB) || max(pubA,pubB) ||
  sharedSecret`, reduced modulo 1,000,000.

Golden plaintext uses UTF-8 JSON with recursively sorted object keys and no
insignificant whitespace. Production decryption accepts semantically valid JSON
regardless of key order; canonical output is required for deterministic tests
and content hashing.

## Validation rules not fully expressible in JSON Schema

- Each canonical key name is at most 64 UTF-8 bytes (JSON Schema counts code
  points).
- Decrypted snapshot JSON is at most 65,536 bytes and contains at most 512 key
  entries.
- All counters are non-negative Int64 values. Aggregation saturates at Int64
  max instead of overflowing.
- `localDay` must be a real Gregorian date and remains the source device's
  date-only value; receivers never convert it through UTC.
- Equal `(deviceId, recordId, revision)` plus equal ciphertext hash is
  idempotent. An equal revision with another hash is a conflict; a lower
  revision is stale.
- When `currentSnapshot.recordId` changes at a local-day rollover, the Worker
  first archives the complete previous current envelope persisted on the device
  row, then replaces that row. A client may also include a newer revision of
  the previous record in `archives`; stale or conflicting supplied revisions
  are rejected. This prevents an archive backlog from blocking rollover while
  preserving the old envelope across R2/D1 or response failures.
- Each sync request contains at most 16 archives. Initial bootstrap, recovery,
  and pairing uploads may use multiple requests with `bootstrapComplete=false`;
  the final page omits the field or sets it to `true`. Manual and automatic
  sync cannot leave a bootstrap page open. The Worker-generated rollover
  handoff is not a seventeenth client archive and does not raise this wire cap.
- A device has a lifetime ceiling of 256 cooldown-exempt pages (4,096 archive
  records at the maximum page size). A client must finish on or before that
  boundary; later ordinary sync remains subject to the normal limits.
- The existing-device pairing refresh exemption opens only after the joining
  device is registered and has completed its own bootstrap. This prevents the
  approver from consuming its one refresh while the new device still has no
  history to return.
- Device bearer tokens are generated by clients and use the exact
  `deviceId + "." + base64url(32 random bytes)` form. `/v1/vaults` and
  `/v1/recover` reject a token whose UUID prefix does not equal the request's
  normalized device ID. An exact create/recover retry therefore returns the
  same credential after a lost response instead of orphaning a server-created
  token.
- Recovery returns `cursor: 0`. With `replaceDeviceId == deviceId`, it rotates
  an active or revoked same-vault identity in place, preserves its encrypted
  current/history records, resets only its bootstrap/idempotency state, and
  returns its accepted `currentSnapshot` when present. A missing target returns
  `replace_device_not_found`; it never silently falls back to a new identity.
  At five active devices, an authenticated `maximum_devices` error includes
  `vaultId` and the five encrypted device descriptors so the client can decrypt
  names and explicitly retry as a takeover. The encrypted profile is deferred
  to the first recovery `/sync` because its AAD requires the returned vault ID.
- Pairing may similarly take over a same-vault device ID. Join/complete expose
  `replacedExistingDevice`; completion rotates that row without duplicating its
  contribution. A completed session continues returning the approving public
  key and encrypted grant for exact retries until its ten-minute expiry.
- Authenticated `GET /v1/state` is read-only: it does not consume sync quota or
  mutate timestamps, and returns active device descriptors plus accepted
  current records for all active devices, including the caller. This lets a
  recovered or repaired client rebuild revisions before its first upload.
- Vault deletion atomically stores a hash-only receipt for the initiating
  device token before tombstoning the vault. The receipt has no vault foreign
  key, survives physical D1/R2 deletion for 30 days, and can only repeat
  `DELETE /v1/vault` with `204`; every other endpoint still returns `401`.
  Receipt expiry cleanup removes at most 100 rows per Cron invocation.
- A sync response sets `historyHasMore` when the inline history page is not
  complete. Clients persist its cursor and continue through `/v1/history`,
  including after an ordinary manual or automatic sync.
- Ordinary manual/automatic sync is rejected while the vault has fewer than
  two active devices. The `single_device_sync_disabled` 409 response includes
  `activeDeviceCount: 1`; clients persist it and stop ordinary timers/manual
  sync. Pairing and recovery are unaffected.
- Wire-visible revisions and cursors are limited to the interoperable JSON
  safe-integer range (`0...9,007,199,254,740,991`; revisions start at 1).

Run `npm run contracts:check` from `services/sync-worker` to compile the JSON
Schemas, validate fixtures, verify OpenAPI references, and recompute the golden
cryptographic values with the Node.js standard library.
